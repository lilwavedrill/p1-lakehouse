## 2. Поднятые сервисы — и почему именно они

`docker ps` показывает lakehouse-minio, lakehouse-pg, lakekeeper, trino. Spark поднимал отдельно, только на время п.6.2.

| Сервис | Роль в стеке | Почему именно он (а не альтернатива) |
|---|---|---|
| MinIO | S3-совместимое объектное хранилище (сюда физически падают parquet-файлы) | Говорит по протоколу S3, поэтому и Trino, и Spark к нему подключаются как к обычному облаку, ничего не перенастраивая. Если потом переезжать в настоящий S3, поменяется только адрес. Бесплатный. Официальный образ сейчас отдает 401, пришлось взять bitnamilegacy/minio, внутри тот же MinIO |
| PostgreSQL | БД, где Lakekeeper хранит метаданные каталога | Тут без выбора, Lakekeeper хранит каталог только в Postgres. Но это и хорошо: каталог должен меняться транзакционно, иначе две записи в таблицу могут затереть друг друга |
| Lakekeeper | Iceberg REST Catalog — каталог метаданных таблиц | Каталог по открытому REST-протоколу Iceberg, значит к нему может подключиться любой движок, а не только Trino. В п.6.2 я это проверил на Spark - он увидел мои таблицы без всякого экспорта. Hive Metastore тоже бы подошел, но он тяжелее и тянет за собой Hadoop |
| Trino | SQL-движок: ходит в Lakekeeper за метаданными и читает/пишет данные в MinIO | Быстрый на интерактивных запросах, и в нем есть встроенный генератор tpch - данные не надо никуда скачивать. Все слои у меня это обычный SQL. По Q16 он заметно быстрее Spark: по bronze у Trino 3.5-4.8 с на холодную (смотря какой кодек), у Spark 10 с |
| Spark (tabulario/spark-iceberg) | второй движок, читает те же таблицы (п.6.2) | Нужен был, чтобы показать, что данные открытые и их читает не только Trino |

### Скрипты, которыми поднимал стек

Целиком - `stand/up.sh`. Главное оттуда:

```bash
# MinIO - объектное хранилище
docker run -d --name lakehouse-minio --add-host host.docker.internal:host-gateway \
  -p 9000:9000 -p 9001:9001 \
  -e MINIO_ROOT_USER=minioadmin -e MINIO_ROOT_PASSWORD=minioadmin \
  -v minio-data:/bitnami/minio/data bitnamilegacy/minio:latest

# PostgreSQL - метаданные Lakekeeper. Порт 5433, потому что на 5432 у меня уже свой postgres 14
docker run -d --name lakehouse-pg --add-host host.docker.internal:host-gateway \
  -e POSTGRES_PASSWORD=postgres -p 5433:5432 \
  -v pg-data:/var/lib/postgresql/data postgres:17

# Lakekeeper - сначала migrate, потом serve
docker run -d --name lakekeeper --add-host host.docker.internal:host-gateway \
  -e 'LAKEKEEPER__PG_ENCRYPTION_KEY=This-is-NOT-Secure!' \
  -e 'LAKEKEEPER__PG_DATABASE_URL_READ=postgresql://postgres:postgres@host.docker.internal:5433/postgres' \
  -e 'LAKEKEEPER__PG_DATABASE_URL_WRITE=postgresql://postgres:postgres@host.docker.internal:5433/postgres' \
  -p 8181:8181 quay.io/lakekeeper/catalog:latest serve

# Trino - со своим jvm.config (heap 2 ГБ), иначе его убивал OOM
docker run -d --name trino --add-host host.docker.internal:host-gateway -m 2900m -p 8080:8080 \
  -v "$(pwd)/catalog:/etc/trino/catalog" \
  -v "$(pwd)/conf/jvm.config:/etc/trino/jvm.config" \
  -v "$(pwd)/conf/config.properties:/etc/trino/config.properties" \
  trinodb/trino:476
```

Каждый слой у меня в своем бакете (bronze/silver/gold), со своим warehouse в Lakekeeper и своим каталогом в Trino (`stand/catalog/*.properties`). То есть слои разделены физически, а не просто схемами.

Что пошло не по гайду:
- Lakekeeper падал на миграции с `syntax error at or near "NULLS"`. Долго не мог понять почему. Оказалось, контейнеры по `host.docker.internal:5432` попадали не в контейнерный postgres 17, а в мой старый postgres 14 с Homebrew, а он такой синтаксис не знает. Перенес контейнер на 5433.
- Trino падал с кодом 137, это OOM. По умолчанию он берет 80% памяти, на моих 8 ГБ это слишком. Поставил `-Xmx2G`.
- Когда рядом запускал Spark, Trino опять убило. Два движка одновременно на 8 ГБ не помещаются, гонял по очереди.

## 3. Разбор запроса — какие данные нужны

| Таблица TPC-H | Нужные колонки | Что запрос с ними делает (фильтр / джойн / агрегат / вывод) |
|---|---|---|
| part | partkey | джойн с partsupp |
| part | brand, type, size | фильтры (`brand <> 'Brand#45'`, `type NOT LIKE 'MEDIUM POLISHED%'`, `size IN (...)`), группировка и вывод |
| partsupp | partkey, suppkey | джойн с part, по suppkey считается `count(DISTINCT)` |
| supplier | suppkey, comment | подзапрос: в comment ищем жалобы, таких поставщиков выкидываем через `NOT IN` |

Остальные колонки (цены, адреса, телефоны и т.д.) запросу не нужны, поэтому дальше bronze они не идут.

## 6. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос | Твой ответ  |
|---|---|
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)? | В обычной БД данные лежат на ее дисках и в ее формате, достать их можно только через саму эту БД. Хранение и вычисления склеены, и масштабировать их приходится вместе. В lakehouse файлы лежат в дешевом S3 в открытом формате, а движок отдельно. Я это на практике увидел: одни и те же таблицы читают Trino и Spark, и я ничего никуда не копировал. А Iceberg сверху добавляет то, чего у просто кучи parquet-файлов нет - транзакции, версии, откат |
| Пример schema evolution на Silver: добавил/переименовал колонку — что произошло? | На `silver.lakehouse.dim_supplier` сделал `ADD COLUMN region`. У старых строк стало NULL, а файл с данными как был один, так и остался, ничего не переписывалось. Потом `RENAME COLUMN name TO supplier_name`, и старые данные сразу читаются под новым именем. Так работает, потому что Iceberg помнит колонки по id, а не по названию. Новых снапшотов при этом не появилось - смена схемы это только новая версия метаданных. Весь вывод в `results/p1_evolution_output.txt` |
| Пример скрипта восстановления данных из снапшота (time travel) | см. ниже |

Восстановление (целиком - `scripts/p1_evolution.sh`):

```sql
-- запомнил текущий снапшот
SELECT snapshot_id FROM silver.lakehouse."dim_supplier$snapshots"
ORDER BY committed_at DESC LIMIT 1;          -- 4256117099757477496

-- "авария": удалил почти все
DELETE FROM silver.lakehouse.dim_supplier WHERE has_complaint = false;
-- осталось 56 строк из 100 000

-- посмотреть, как было до удаления
SELECT count(*) FROM silver.lakehouse.dim_supplier
FOR VERSION AS OF 4256117099757477496;        -- 100 000

-- откатить таблицу
ALTER TABLE silver.lakehouse.dim_supplier
EXECUTE rollback_to_snapshot(4256117099757477496);
-- снова 100 000 (56 с жалобами + 99 944 без)
```

После отката в `$history` снапшот с удалением помечен `is_current_ancestor = false`. Он никуда не делся из истории, просто таблица на него больше не смотрит. Еще интересно: откат вернул данные, но не схему, region и supplier_name остались. Логично, раз смена схемы снапшоты не создает.

### 6.2. Подключить инструмент к lakehouse

| Инструмент | Почему выбрал именно его |
|---|---|
| Spark 3.5 (образ tabulario/spark-iceberg) | Сначала хотел Metabase, но у него нет встроенного драйвера для Trino, только сторонний плагин. Spark умеет читать Iceberg сам, напрямую из Lakekeeper, Trino ему вообще не нужен. Мне это даже больше понравилось - видно, что данные не заперты в одном движке. Для моей задачи Trino все равно лучше: Q16 по bronze у Trino 3.5-4.8 с на холодную, у Spark 10 с. Spark скорее для тяжелых пакетных расчетов, где важнее не упасть, чем ответить быстро |

Запуск:

```bash
docker run --rm --name p1-spark --add-host host.docker.internal:host-gateway \
  -m 1900m --entrypoint spark-submit \
  -e AWS_REGION=us-east-1 -e AWS_ACCESS_KEY_ID=minioadmin -e AWS_SECRET_ACCESS_KEY=minioadmin \
  -v "$(pwd)/scripts/p1_spark_bronze.py:/home/iceberg/p1_spark_bronze.py" \
  tabulario/spark-iceberg:latest \
  --driver-memory 1200m /home/iceberg/p1_spark_bronze.py
```

Как подключал - в `scripts/p1_spark_bronze.py`: каталог `bronze` типа rest на `http://host.docker.internal:8181/catalog`, warehouse `bronze`, S3 на MinIO. С первого раза не взлетело, упало с `UnknownHostException: rest`. Оказалось, в этом образе по умолчанию прописан чужой каталог demo с адресом rest. Поставил `spark.sql.defaultCatalog = bronze`, и заработало.

Что Spark увидел в bronze (вывод в `results/p1_spark_output.txt`):
- `SHOW TABLES` - raw_part, raw_partsupp, raw_supplier;
- строк 2 000 000 / 8 000 000 / 100 000, как и в Trino;
- в схеме на месте мои служебные loaded_at и source_system;
- Q16 по bronze в Spark дал 27 840 строк и сумму 1 186 339. Ровно как gold в Trino.

## 7. Выводы

Главное, что мне дал медальон: сырые данные никуда не деваются. Когда я переделывал silver под нормализацию, в bronze не поменял ни строчки кода, переписал только silver и gold. Пересобрал - и gold сошелся с оригиналом до строки. Gold весит 0.08 МБ против 290 МБ в bronze и отвечает примерно за 0.05 с.

Про сжатие понял, что "меньше места" и "быстрее читается" - не одно и то же. У меня ZSTD вышел больше GZIP на 8%, но на холодную читался быстрее всех. А без сжатия ни разу не оказалось лучшим: ни по месту, ни по записи, ни по чтению, хотя я ожидал, что хотя бы пишется оно быстрее.
